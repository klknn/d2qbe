# betterC な D言語コンパイラ d2qbe を作って、AI と育てて、Wasm でゲームを動かすまで

この記事は [D言語 Advent Calendar 2026](https://qiita.com/advent-calendar/2026/dlang) の記事です。

2026年の1月から、趣味で D言語（`-betterC` サブセット）のコンパイラ **[d2qbe](https://github.com/klknn/d2qbe)** を作っている。最初は有名な『低レイヤを知りたい人のためのCコンパイラ作成入門』（いわゆる compilerbook）を参考に、人間（私、klknn）が休日に少しずつ手で書いていた小さなトイコンパイラだった。それが途中から AI エージェントと一緒にフロントエンドを拡張してセルフホスティングを達成し、最終的には依存していたバックエンド（QBE）まで D言語で書き直して、ブラウザや WASM-4 上で D言語製のゲームが動くところまで来てしまった。

現在のコード規模はフロントエンド（[`source/d2qbe/`](https://github.com/klknn/d2qbe/tree/2213910/source/d2qbe)）が約 6,250 行、自前バックエンド（[`source/dqbe/`](https://github.com/klknn/d2qbe/tree/2213910/source/dqbe)）が約 4,850 行、合計で約 11,100 行の `-betterC` な D言語コードになっている。

この記事では、2026年1月から8月にかけてのこのプロジェクトの経緯を、だいたい時系列に沿って以下の 3 章で振り返る。

1. **第1章：人間が compilerbook を片手に QBE バックエンドで書き始めた頃（2026年1月〜2月）**
2. **第2章：AI にフロントエンドの泥臭い部分を任せつつ、スタイルと開発環境を共有した話（2026年6月）**
3. **第3章：QBE バックエンドまで自前で書き（`dqbe`）、Wasm 対応とゲーム実行まで行った話（2026年6月〜8月）**

派手なベンチマークやバズを狙った話ではなく、「こういう動機で始めて、こういうところで手が止まり、こうやって環境を整えたらここまで進んだ」という記録である。

## 第1章：compilerbook を D言語 + QBE でなぞっていた頃（2026年1月〜2月）

### なぜ x86-64 ではなく QBE を選んだのか

コンパイラ自作の入門書として、[低レイヤを知りたい人のためのCコンパイラ作成入門](https://www.sigbus.info/compilerbook)（rui314 氏の `9cc` / `chibicc` の解説書）はとてもよくできている。小さなステップごとにテストが通るようになり、少しずつ言語機能が増えていく設計は、趣味プロジェクトとしてモチベーションが維持しやすい。

ただ、この本をそのままなぞるにあたって、2 つだけ自分なりのアレンジを入れた。

1 つ目は実装言語を C ではなく **D言語（`-betterC`）** にしたこと。普段から D言語を書いていたし、GC やランタイムに頼らない `-betterC` なら、C とほぼ同じ感覚で書けてセルフホスティングのハードルも下がる。それでいて `final switch` や `module`、組み込みの `unittest` など、C より少しだけ書きやすい道具が手元にある。

2 つ目がターゲットの選択で、**x86-64 アセンブリを直接吐くのではなく、[QBE](https://c9x.me/compile/) の中間表現（QBE IR）を吐く**ことにした。

理由はわりと単純だ。1 つは、LLVM IR みたいな SSA 形式の中間表現を吐くコンパイラの方が単純にかっこいいと思ったからである。もう 1 つは、教科書通りに x86-64 だけをターゲットにしてスタックマシン風のコード生成をなぞるのは、少し退屈に感じたからだった。QBE を挟めば、フロントエンド側はレジスタ割り当てや呼び出し規約の細部から解放され、しかも x86-64 だけでなく ARM64（手元の Apple Silicon Mac を含む）でもそのまま動くバイナリが得られる。

LLVM そのものをバックエンドにする手もあったが、LLVM は API もビルドも巨大で、週末の趣味プロジェクトとしては重すぎる。その点、QBE は C で書かれたコンパクトなコンパイラバックエンドで、テキスト形式の SSA IR を標準入力から食わせるとアセンブリを吐いてくれる。`./d2qbe` の出力をパイプで `./qbe/qbe` に渡し、最後に `cc` でリンクするだけという構成は、コンパイラの各フェーズの境界がはっきり見えて気持ちよかった。

```bash
./d2qbe "main { return 0; }" > a.ssa
./qbe/qbe < a.ssa > a.s
cc a.s -o a.out
./a.out
```

QBE IR 自体も素直だ。型は基本的に 32-bit 整数の `w`、64-bit 整数／ポインタの `l`、単精度・倍精度浮動小数点の `s` / `d` の 4 つしかない。たとえばスタックにローカル変数を確保して値を書き込むコードは次のように書ける。

```qbe
export function w $main() {
@start
  %x_addr =l alloc4 4
  storew 42, %x_addr
  %t1 =w loadw %x_addr
  ret %t1
}
```

LLVM IR に比べると命令数も型システムもずっと小さく、仕様書（[QBE Intermediate Language](https://c9x.me/compile/doc/il.html)）は 1 ページで全体像がつかめる。

### 最初の 3 週間と、人間が作ったコードの「型」

最初のリポジトリ初期化は 2026年1月26日（[`ec74767`](https://github.com/klknn/d2qbe/commit/ec74767)）だった。そこからのコミット履歴を見ると、compilerbook のステップをかなり忠実に追いかけている。

- 1月27日：ステップ 3（加減算）完了
- 1月29日：エラー位置を `^` で指すエラーメッセージ実装、`-betterC` 互換性修正
- 2月1日：ステップ 5〜7（四則演算、単項 `+-`、複数文字の比較演算子）
- 2月2日：ファイル分割（`tokenize.d`, `parse.d`, `codegen.d`）、ステップ 9〜10（ローカル変数）
- 2月3日〜5日：ステップ 11〜12（`return`, `if`, `while`, `for`, ブロック）
- 2月7日〜8日：ステップ 14（複数 `int` 引数の関数呼び出し）
- 2月15日：ポインタのアドレス取得・参照外し（[`a59a9c7`](https://github.com/klknn/d2qbe/commit/a59a9c7) `wip pointer addr/deref`）

この時点で実装のスタイルはほぼ固まっていた。`klknn/human` ブランチとして残っている当時の [`source/d2qbe/tokenize.d`](https://github.com/klknn/d2qbe/blob/a59a9c7/source/d2qbe/tokenize.d) を見ると、D言語で書かれているとはいえ中身はかなり C に近い。

```d
enum TokenKind {
  reserved,
  ident,
  num,
  eof,
}

struct Token {
  TokenKind kind;
  Token* next;
  int val;
  char* str;
  int len;
}

Token* token;
```

`core.stdc.stdio` や `core.stdc.stdlib` をそのまま使い、トークンは `Token*` の単方向連結リスト、パーサは再帰下降、テストは [`test/run.sh`](https://github.com/klknn/d2qbe/blob/a59a9c7/test/run.sh) に `assert <期待する終了コード> "<Dコード>"` をずらっと並べてシェルスクリプトで回す。ビルドは [`Makefile`](https://github.com/klknn/d2qbe/blob/a59a9c7/Makefile) に `ldc2 -g -w -betterC` を書いただけの単純な構成だ。

この素朴さは、あとから振り返るととても重要な土台になった。複雑な抽象化や D言語固有の高度なメタプログラミングを避けていたおかげで、「このコンパイラ自身をこのコンパイラでコンパイルする」というセルフホスティングのゴールが現実的な距離に収まっていたからだ。

### そして 4 ヶ月止まった

ただ、2月15日の「ポインタの参照外しを書きかけ」のコミット（[`a59a9c7`](https://github.com/klknn/d2qbe/commit/a59a9c7)）を最後に、開発はいったんピタッと止まった。

理由はありふれている。ここから先は「型システム」「ポインタ演算と配列」「グローバル変数」「文字列リテラル」「構造体とメモリレイアウト」と、急にフロントエンドの泥臭い仕事が増えるゾーンに入る。compilerbook を読んだことがある人なら分かると思うが、四則演算や `if`/`for` の頃はコード量も少なくて楽しいのに、型と宣言のパース、構造体のアライメント計算、コード生成側の暗黙変換あたりから一気に実装の細部が増えて手が重くなる。本業の合間に細切れの時間で向き合うには、少し億劫なフェーズに入ってしまったのである。

## 第2章：AI とフロントエンドを育てる——スタイルと開発環境の共有（2026年6月）

### 4 ヶ月ぶりの再開と、当時の AI プラン・環境

開発が再開したのは 4 ヶ月後の 2026年6月20日（[`8c862de`](https://github.com/klknn/d2qbe/commit/8c862de)）だった。ここで方針を変え、フロントエンドの大変な部分の実装を AI コーディングエージェントに任せてみることにした。

使っていた AI のプランについても軽く触れておくと、最初は無料プラン（Gemini Flash 系など）で様子を見ながら始め、手応えがつかめてセルフホスティングやバックエンド開発まで広げるにつれて Google AI Pro 相当の有料プランに移行した。さらに後半のバックエンド ABI 修正や Wasm 対応では Codex も併用している（[`docs/codex.md`](https://github.com/klknn/d2qbe/blob/2213910/docs/codex.md) にその作業ログが残っている）。高価な専用環境を最初から組んだわけではなく、個人の趣味開発の延長で手が届く範囲のプランから段階的に広げた形だ。

### 「丸投げしない」ための 3 つの整備

とはいえ、既存のコードベースにいきなり「セルフホスティングできるようにして」と投げてもうまくいかないことは目に見えている。既存の `d2qbe` には人間が作ったコーディングスタイル（`-betterC`、グローバル変数と連結リスト中心、依存ゼロ）と、小さくテストを回す開発ループがある。これを崩さずに機能を増やすために、最初にやったのは実装ではなく**開発環境と約束事の整備**だった。

#### 1. ステージ分割した計画書と TDD の徹底
まず [`docs/plan.md`](https://github.com/klknn/d2qbe/blob/2213910/docs/plan.md) にセルフホスティングまでのロードマップを書き、Stage 1（型・ポインタ宣言・スタック変数）、Stage 2（ポインタ演算・添字・キャスト）、Stage 3（`sizeof`・グローバル変数・文字列リテラル）、Stage 4（構造体・列挙型）と細かく区切った。各ステージごとに [`docs/stage1.md`](https://github.com/klknn/d2qbe/blob/2213910/docs/stage1.md)〜[`docs/stage4.md`](https://github.com/klknn/d2qbe/blob/2213910/docs/stage4.md) のような設計メモを作り、「まずテストを追加して失敗させ、そのあと実装を通す」という手順を固定した。

#### 2. テストを 1 秒未満で回せる `make unittest` の導入
初期のテストは [`test/run.sh`](https://github.com/klknn/d2qbe/blob/2213910/test/run.sh) によるエンドツーエンドの結合テストだけだった。しかし macOS 上で何十ケースもの小さな D プログラムを毎回 `d2qbe` → `qbe` → `cc`（リンカ）と通すと、プロセス起動とリンクのオーバーヘッドが積み重なってフィードバックが遅い。

AI エージェントは修正とテストのサイクルを大量に回すので、テストが遅いとそれだけで開発効率が落ちる。そこで [`Makefile`](https://github.com/klknn/d2qbe/blob/2213910/Makefile) に `make unittest` を追加し、D言語組み込みの `unittest` ブロックを `ldc2 -unittest -main` でビルドしてインメモリで実行する仕組みを整えた。これでトークナイザ、パーサの演算子優先順位、構造体のレイアウト計算といった検証が 1 秒未満で終わるようになり、結合テスト（`make test`）はチェックポイントとして使う運用にできた。

#### 3. リポジトリ内にスキルと引き継ぎ書を置く
エージェントのセッションが変わるたびに同じ前提を説明し直すのは不毛なので、[`.agents/skills/`](https://github.com/klknn/d2qbe/tree/2213910/.agents/skills) 以下にプロジェクト固有のガイドラインを置いた。

- [`.agents/skills/d/SKILL.md`](https://github.com/klknn/d2qbe/blob/2213910/.agents/skills/d/SKILL.md): サポートする `-betterC` サブセットの型サイズや仕様
- [`.agents/skills/qbe/SKILL.md`](https://github.com/klknn/d2qbe/blob/2213910/.agents/skills/qbe/SKILL.md): `d2qbe` が吐く QBE IR の規約（`w`/`l`/`s`/`d`、`alloc4`/`alloc8`、`data` セクションの書式）
- [`.agents/skills/testing/SKILL.md`](https://github.com/klknn/d2qbe/blob/2213910/.agents/skills/testing/SKILL.md): `make unittest` を先に書く TDD ルールと `make test` の使い分け

さらに [`docs/handover.md`](https://github.com/klknn/d2qbe/blob/2213910/docs/handover.md) という引き継ぎドキュメントを用意し、完了した機能、未実装の機能、テストの回し方、`d2qbe` が生成する QBE IR のサブセット仕様を逐一更新するようにした。結果的にこれは AI のためだけでなく、数日ぶりにリポジトリを触る人間にとっても非常にありがたいドキュメントになった。

### 1日でセルフホスティング、数日で実用的な betterC サブセットへ

このレールを敷いてみると、開発のスピードは想像以上だった。6月20日のコミットログを振り返ると、Stage 1、Stage 2、Stage 3、`assert`、`break`/`continue` と順番にテストを通し、その日のうちに最初のセルフホスティング（[`13b5cc5`](https://github.com/klknn/d2qbe/commit/13b5cc5) `Achieve self-hosting for d2qbe compiler`）に到達している。

セルフホスティングの検証スクリプト（[`test/self_host.sh`](https://github.com/klknn/d2qbe/blob/2213910/test/self_host.sh)）がやっていることは単純明快だ。

1. `ldc2` でビルドしたブートストラップ版 `./d2qbe` を使って、`d2qbe` 自身のソース（[`source/d2qbe/app.d`](https://github.com/klknn/d2qbe/blob/2213910/source/d2qbe/app.d) から再帰的に import を解決）をコンパイルし、QBE IR を吐かせる。
2. それを `qbe` と `cc` でビルドして、セルフホスト版バイナリ `./test/d2qbe_self_hosted` を作る。
3. そのセルフホスト版コンパイラを使って [`test/run.sh`](https://github.com/klknn/d2qbe/blob/2213910/test/run.sh) の全結合テストを実行し、全ケースが通ることを確認する。

セルフホスティングが一度通ると、「新しい機能を入れるたびに、コンパイラ自身をコンパイルし直しても壊れないか」という強力な回帰テストが手に入る。そこから数日（6月20日〜24日）で、D言語らしい機能が次々と入った。

- 構造体、メンバー関数（`_D_struct_StructName_funcName` にマングリングして暗黙の `this` ポインタを渡す）、コンストラクタ／デストラクタ（RAII）
- `switch` 文、三項演算子（フロントエンド側で QBE の `phi` 命令を直接吐く最適化も追加）
- 多次元静的配列、スライス `T[]`（`{ size_t length; T* ptr; }` の 16 バイト構造体として表現）
- `alias`、型プロパティ（`.sizeof`, `.init`, `.alignof`）、`static assert`
- `version` / `debug` による条件付きコンパイル
- `auto` による型推論
- テンプレート（`template Name(T) { ... }` と単一型引数の eponymous テンプレート `Name!Arg` をトークン列の複製＋置換で展開）
- `module` と再帰的な `import` によるモジュール分割コンパイル
- 浮動小数点（`float`, `double`）
- `foreach` / `foreach_reverse`（パーサ内で通常の `for` ループに展開）
- `scope(exit)`（ブロック脱出時・`return` 時に登録された後処理文を LIFO 順で展開。例外機構がない `-betterC` 仕様に合わせて `scope(success)` / `scope(failure)` はコンパイルエラーにする）

もちろん、D言語の `-betterC` 仕様のすべてを網羅しているわけではない。`ref` パラメータ、UFCS、CTFE、クロージャ／デリゲート、`extern(C++) class`、複数引数の複雑なテンプレートなどはまだ未対応だ。それでも、`collatz`、素数判定、N-Queens、マンデルブロ集合といったベンチマークや、コンパイラ自身（数千行規模）が普通にコンパイルできる水準まではあっという間に到達した。

面白かったのは、AI が書いたコードであっても、最初に人間が作った「C 風の素朴な betterC スタイル」と「`Makefile` + `unittest` + `test/run.sh`」の枠組みから大きく逸脱しなかったことだ。セルフホスティングという制約自体が「高度な言語機能を使って賢すぎるコードを書くこと」への自然な歯止めになっており、結果的にフロントエンド全体（[`source/d2qbe/parse.d`](https://github.com/klknn/d2qbe/blob/2213910/source/d2qbe/parse.d) や [`source/d2qbe/codegen.d`](https://github.com/klknn/d2qbe/blob/2213910/source/d2qbe/codegen.d)）が読みやすい構造を保ったまま育っていった。

## 第3章：QBE バックエンドも自前で書いて（`dqbe`）、Wasm でゲームを動かすまで（2026年6月〜8月）

### 「せっかくだし QBE も D言語で書いてみよう」—— `dqbe` の誕生

フロントエンドがセルフホスティングできてくると、次に気になるのはパイプラインの真ん中に居座っている外部依存、すなわち C で書かれた本家 `qbe/qbe` の存在だった。

「`d2qbe` が吐く QBE IR のサブセット自体はそんなに広くない。だったら QBE バックエンドも `-betterC` な D言語で自前実装して、フロントエンドからアセンブリ生成まで全部自分のコードでセルフホスティングできたら面白いのではないか」

こうして生まれたのが [`source/dqbe/`](https://github.com/klknn/d2qbe/tree/2213910/source/dqbe)、通称 **`dqbe`** である（初回実装は [`26ff909`](https://github.com/klknn/d2qbe/commit/26ff909)）。

最初のバージョン（6月20日）は、徹底的にシンプルさに振った設計にした（[`docs/dqbe.md`](https://github.com/klknn/d2qbe/blob/2213910/docs/dqbe.md)）。QBE IR をトークナイズ・パースし、すべての仮想レジスタ（一時変数 `%tN`）をフレームポインタ `%rbp` 相対の 8 バイトスタックスロットに 1 対 1 で割り当てる。演算のたびにスタックから `%rax`/`%rcx` にロードし、命令を実行して、結果をまたスタックに書き戻す。

この「全部スタック方式」は遅い代わりにバグが入りにくい。レジスタ破壊（clobbering）に悩まされずに済むので、まずは正しさを確保し、`./d2qbe` + `./dqbe` の組み合わせで全結合テストとセルフホスティングを通すことができた。

### レジスタ割り当て、ベンチマーク、そして「バイナリが 44MB になった話」

動くものができたら、やはり性能が気になる。[`source/dqbe/regalloc.d`](https://github.com/klknn/d2qbe/blob/2213910/source/dqbe/regalloc.d) に制御フローグラフ（CFG）の構築、生存解析（liveness analysis）、そして **線形スキャンレジスタ割り当て（Linear Scan Register Allocator）** を導入した。x86-64 では callee-saved な汎用レジスタ 5 本（`%rbx`, `%r12`〜`%r15`）と浮動小数点レジスタ 6 本（`%xmm8`〜`%xmm13`）を大域的に割り当て、`phi` 命令は並列コピー（parallel copy）でスワップサイクルを避けながら SSA デコンストラクションする。

`linux/x86_64` 上でマンデルブロ集合の描画ループ（`test/mandel.d` を 50 回実行）を測った結果が以下だ。比較対象は、自前ツールチェイン（`d2qbe` + `dqbe`）、ハイブリッド（`d2qbe` + 本家 `qbe`）、そして本番用コンパイラの `ldc2 -O3 -betterC` である。

| 指標 | 自前 (`d2qbe` + `dqbe`) | ハイブリッド (`d2qbe` + 本家 QBE) | `ldc2 -O3 -betterC` |
| :--- | :---: | :---: | :---: |
| コンパイル時間 | **0.04 s** | 0.06 s | 0.07 s |
| コンパイル時メモリ (Max RSS) | **10.0 MB** | 9.8 MB | 97.7 MB |
| バイナリサイズ (stripped) | 14,536 B | 14,536 B | 14,480 B |
| 実行時間（50回） | 1.36 s | 0.25 s | 0.23 s |

ここから読み取れることは 2 つある。

1 つは、フロントエンドの質と軽さだ。`d2qbe` + 本家 QBE のハイブリッド構成は、実行時間 0.25 秒と `ldc2 -O3`（0.23 秒）に 0.02 秒差まで迫っている。一方でコンパイル時のメモリ消費は LDC2 の約 1/10（10 MB 対 97.7 MB）で済んでいる。

もう 1 つは、自前バックエンド `dqbe` の立ち位置だ。レジスタ割り当てを入れたことでマンデルブロ集合の実行時間は 1.70 秒から 1.36 秒へ約 20% 短縮されたが、本家 QBE（0.25 秒）にはまだ遠く及ばない。最適化パスを本気で積んでいる本家 QBE の実力を肌で実感する結果になった。

また、セルフホスティング時のベンチマーク（[`docs/self_host_benchmark.md`](https://github.com/klknn/d2qbe/blob/2213910/docs/self_host_benchmark.md)）を取っていたときに、個人的にとても気に入っているハマり話がある。

セルフホストされた `dqbe` 込みのバイナリサイズが、ある時点で **764 MB** というとんでもない大きさになっていたのだ。原因は、関数内の命令配列や基本ブロックの配列を巨大な静的グローバル配列として持っていたことだった。命令配列をヒープ確保のポインタに逃がしたところ、`ldc2` でビルドしたバイナリは 721 MB から 1.2 MB まで縮んだ。ところが、自前ツールチェインでビルドしたバイナリはまだ **44 MB** 残っていた。

調べてみると、[`source/dqbe/regalloc.d`](https://github.com/klknn/d2qbe/blob/2213910/source/dqbe/regalloc.d) に残っていた 1 行が犯人だった。

```d
__gshared BasicBlock[1000] blocks;
```

各 `BasicBlock` 構造体が生存解析用の `bool[10000]` 配列を 4 つ（`use`, `def`, `live_in`, `live_out`）持っているので、1 ブロックあたり約 40 KB、1,000 ブロックで約 40 MB になる。普通のコンパイラ（LDC2 や本家 QBE）はゼロ初期化されたグローバル変数を `.bss` セクションに置くため、実行ファイル上のサイズはほぼ 0 バイトで済む。ところが当時の `dqbe` はすべてのグローバル変数を `.data` セクションに `.zero 40000000` として吐いていたため、アセンブラが素直に 4,000 万バイトのゼロをディスク上のバイナリに書き込んでいたのである。

こういう「教科書で読んだ `.bss` と `.data` の違い」が 40 MB のバイナリサイズ差として目の前に現れるのは、バックエンドを自分で書いたからこその醍醐味だった。

### ARM64、Win64、そして WebAssembly (`wasm32`) へ

7月初めには `dqbe` にクロスコンパイルのターゲット切り替え（`-t` / `-mtriple`）を入れ、System V AMD64（[`source/dqbe/sysv.d`](https://github.com/klknn/d2qbe/blob/2213910/source/dqbe/sysv.d)）に加えて ARM64（[`source/dqbe/arm64_abi.d`](https://github.com/klknn/d2qbe/blob/2213910/source/dqbe/arm64_abi.d)、QEMU 上でのテストと macOS Apple Silicon 対応）や Windows Win64（[`source/dqbe/win64.d`](https://github.com/klknn/d2qbe/blob/2213910/source/dqbe/win64.d)）の呼び出し規約にも対応した。レジスタ引数を超えたスタック渡し引数が黙って落ちていたバグを、9 引数のテストを書いて潰したのもこの頃だ（[`docs/codex.md`](https://github.com/klknn/d2qbe/blob/2213910/docs/codex.md)）。

そして 2026年8月、次の一手として始めたのが **WebAssembly（`-t wasm32`）バックエンド**（[`4edc580`](https://github.com/klknn/d2qbe/commit/4edc580)）だった。

ここで最初に決めた制約が 1 つある。**外部ツールチェーンを一切必須にしないこと**だ。WASI SDK も、Emscripten も、`wat2wasm` も、`lld` も要求しない。`dqbe -t wasm32` 自身が標準出力に生の `.wasm` バイナリ（先頭 8 バイトが `00 61 73 6d 01 00 00 00` の Core WebAssembly バイナリ）を直接書き出す。LEB128 エンコーディング、セクションのフレーミング、型テーブルのインターン処理、すべて [`source/dqbe/wasm.d`](https://github.com/klknn/d2qbe/blob/2213910/source/dqbe/wasm.d)（ちょうど 1,000 行）に収めた。

```bash
./d2qbe -t wasm32 'extern(C) int main() { return 42; }' | ./dqbe -t wasm32 > main.wasm
```

この設計で一番気をつけたのが、**QBE の `l` 型（64-bit）と Wasm32 のアドレス（32-bit `i32`）の境界**だった。

従来の `d2qbe` は 64-bit ホスト前提でポインタをすべて QBE の `l`（8 バイト）として生成していた。これを安易に「`wasm32` バックエンド側で `l` を全部 `i32` に読み替える」と、本物の 64-bit 整数が黙って 32-bit に切り詰められるバグになる。逆に `l` を全部 `i64` にすると、Wasm32 の線形メモリ命令（`i32` アドレスを要求する）に渡せない。設計メモ（[`docs/wasm.md`](https://github.com/klknn/d2qbe/blob/2213910/docs/wasm.md)）にも書いたが、どちらの近道も「つけ髭をつけたコンパイラバグ」にしかならない。

そこで、あえて段階を分けた。

1. `dqbe -t wasm32` 側では、曖昧な `l` は黙って変換せず明確にエラーで弾く。
2. フロントエンド `d2qbe` に `-t wasm32` オプション（ターゲット依存データレイアウト）を導入し、ポインタと `size_t` を 4 バイト、スライスを 8 バイトとしてレイアウト計算し、ターゲット由来のアドレスは最初から QBE の `w` として吐くようにした。
3. 制御フローの変換（QBE の任意 CFG → Wasm の構造化制御フロー）には、プログラムカウンタ用のローカル変数と `loop` によるディスパッチャ方式を採用した。出力される Wasm コードは手書きの `if`/`loop` ほど綺麗ではないが、任意の CFG に対して確実に正しく動く。

### ブラウザデモと、D言語だけで書く WASM-4 ゲーム

最小の算術と関数呼び出しから始めて、制御フロー、線形メモリとデータセグメント、ローカル変数確保、文字列のバイトアクセス、未解決の外部呼び出しを Core Wasm の `env.<name>` インポートとして吐く仕組み、符号なし狭幅ストレージ（`ubyte` / `ushort`）と、1 つずつ小さな垂直スライス（テスト先行）で積み上げていった（ガイドラインは [`.agents/skills/wasm-backend/SKILL.md`](https://github.com/klknn/d2qbe/blob/2213910/.agents/skills/wasm-backend/SKILL.md)）。

結果として、8月9日にはブラウザ上で動くテトロミノのデモだけでなく、ファンタジーコンソール **[WASM-4](https://wasm4.org/)** 向けのカートリッジが **D言語ソースだけ** でビルドして遊べるようになった。

[`demo/wasm4/`](https://github.com/klknn/d2qbe/tree/2213910/demo/wasm4) 以下には、以下のようなカートリッジが入っている。

- [`tetromino.d`](https://github.com/klknn/d2qbe/blob/2213910/demo/wasm4/tetromino.d)（35行）
- [`minicraft.d`](https://github.com/klknn/d2qbe/blob/2213910/demo/wasm4/minicraft.d)（37行）
- [`flight.d`](https://github.com/klknn/d2qbe/blob/2213910/demo/wasm4/flight.d)（33行）
- [`snake.d`](https://github.com/klknn/d2qbe/blob/2619ebf/demo/wasm4/snake.d)（130行：WASM-4 公式スネークチュートリアルの D 移植、[`2619ebf`](https://github.com/klknn/d2qbe/commit/2619ebf)）
- [`samegame.d`](https://github.com/klknn/d2qbe/blob/3a74ca0/demo/wasm4/samegame.d)（約340行：連結グループ探索・重力落下・列詰めまで書いた SameGame、[`3a74ca0`](https://github.com/klknn/d2qbe/commit/3a74ca0)）

WASM-4 のメモリマップド I/O（フレームバッファやゲームパッド入力、描画 API の `env` インポート）は、わずか 20 行の [`demo/wasm4/wasm4.d`](https://github.com/klknn/d2qbe/blob/2213910/demo/wasm4/wasm4.d) で宣言しているだけだ。それを `d2qbe -t wasm32` と `dqbe -t wasm32` にパイプで流し込むだけで、C コンパイラも Wasm リンカも一切介さずに `.wasm` カートリッジが出来上がる。

```bash
make wasm4-samegame
```

これで手元のブラウザが開いて、自分が 1 月に四則演算から書き始めたコンパイラでビルドされた SameGame が動くのを見たときは、さすがにちょっと感慨深かった。

ちなみに「`d2qbe` 自身を `wasm32` にコンパイルしてブラウザ上でセルフホスティングする」というプローブも試している。現時点では可変長引数の `fprintf`（Core Wasm には可変長引数の関数型がないため、`env` インポートのシグネチャ衝突で意図的に止めている）が最初の壁として見えている状態だ。ここを固定引数の診断用シムに整理すれば、ブラウザ内で動くセルフホスト D コンパイラも射程圏内に入ってきている。

## おわりに

1月に「LLVM みたいでかっこいいし、x64 だけは退屈だから」と QBE を選んで書き始めたコンパイラが、まさか同じ年のうちにセルフホスティングして、QBE バックエンドまで自前で書き直し、Wasm バイナリを直接吐いてゲームを動かすようになるとは思っていなかった。

振り返ってみると、このプロジェクトが途中で破綻せずにここまで来られた理由は、わりと地味なところに集約される。

- **最初の土台を小さく単純に保ったこと**：`-betterC`、外部依存なし、素朴なデータ構造。これがセルフホスティングを現実的にした。
- **AI との協業を「環境設計」から始めたこと**：プロンプトの工夫よりも、1 秒未満で回る `make unittest`、明文化した [`docs/plan.md`](https://github.com/klknn/d2qbe/blob/2213910/docs/plan.md)・[`docs/handover.md`](https://github.com/klknn/d2qbe/blob/2213910/docs/handover.md)・[`.agents/skills/`](https://github.com/klknn/d2qbe/tree/2213910/.agents/skills)、そしてテスト先行の小さなコミット粒度が圧倒的に効いた。
- **曖昧なショートカットを避けたこと**：セルフホスティングの回帰テストや、Wasm32 での `l` 型の厳格な拒否のように、「怪しいものを黙って通さない」ルールを置いたおかげで、コードが 1 万行を超えてもデバッグ不能にならなかった。

コンパイラ自作は、昔は「気合を入れて長い連休を何個も溶かす遊び」だったが、テスト環境と設計の境界さえ人間が握っていれば、AI と一緒に自分のペースでかなり遠くまで行ける時代になったと感じている。`d2qbe` もまだ `ref` や CTFE、ブラウザ上での完全セルフホスティングなど残りの宿題は多いので、来年もぼちぼち続けていくつもりだ。
